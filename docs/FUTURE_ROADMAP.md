# Future Roadmap — จาก Go Basic สู่ Back-end และ Gateway

**สถานะ: ยังเป็นแผน** บทเรียน API, Database, MQTT และ Gateway ยังไม่ได้จัดทำ เริ่มเรียนได้ที่ [Phase 1](playlist-01-go-basic/README.md)

## ภาพรวมและศัพท์ก่อนใช้

**Back-end** คือโปรแกรมฝั่งบริการที่ประมวลผลและจัดการข้อมูล, **API** คือช่องทางที่โปรแกรมอื่นใช้เรียกความสามารถของมัน, **Database** คือระบบเก็บและค้นข้อมูลอย่างมีโครงสร้าง ดังนั้นบริการเดียวอาจมีทั้งกฎการทำงาน API และการใช้ฐานข้อมูล แต่เราจะแยกเรียนทีละส่วน

Phase 1 Basic → Phase 2 โปรแกรมและกฎการทำงาน → Phase 3 API → Phase 4 Database → Phase 5 Gateway ที่ส่งข้อมูลไปยังบริการซึ่งบันทึกได้แล้ว

แต่ละเฟสต่อยอดจาก **ข้อมูลการวัดของอุปกรณ์จำลอง** เช่น ค่าอุณหภูมิ เริ่มจากประมวลผลข้อมูล แล้วเพิ่มการรับส่งและบันทึกข้อมูลทีละส่วน

## Phase 2 — Practical Go / Application Core

เริ่มหลังมีพื้นฐาน Phase 1 แล้ว **Core** ในที่นี้หมายถึงส่วนที่ประมวลผลข้อมูล เช่น ตรวจค่าหรือคำนวณสถานะ ก่อนนำไปใช้กับ API และฐานข้อมูล

| เป้าหมายย่อย | สิ่งที่จะทดลอง | ต่อยอด |
|---|---|---|
| Configuration และ JSON | อ่านหนึ่งค่า → ตรวจค่าขาด/ผิด → รายการอุปกรณ์ | เปลี่ยนการตั้งค่าโดยไม่แก้โค้ด |
| ไฟล์และ log | เขียนหนึ่งรายการ → อ่านกลับ → ตรวจเขียนไม่ได้ | ประวัติการทำงานและพื้นฐานคิว |
| แยกกฎจากแหล่งข้อมูล | ส่งตัวอ่านเข้าฟังก์ชัน ใช้ interface จาก Phase 1 เมื่อจำเป็น แล้วสลับเป็นตัวจำลอง | ทดสอบกฎโดยไม่พึ่งเครือข่าย |
| HTTP client และ timeout | เรียก localhost → server ช้า → จำกัดเวลารอ | ไปใช้บริการ API ใน Phase 3 |
| งานพร้อมกัน | แบ่งงานด้วย goroutine รับผลด้วย channel และยกเลิกด้วย context | อ่านหลายอุปกรณ์และยกเลิกงาน |
| การหยุดโปรแกรม | หยุดรับงาน → รอ/ยกเลิก → ปิดทรัพยากร | graceful shutdown และตรวจ data race เมื่อรองรับ |

ผลลัพธ์ที่ตั้งใจไว้: โปรแกรมที่รันใน terminal อ่านข้อมูลตามไฟล์ตั้งค่า จัดการข้อผิดพลาด และทดสอบส่วนประมวลผลได้

## Phase 3 — Go Back-end & REST API

**HTTP** เป็นกติกาการรับส่ง request/response ส่วน **REST API** ในเส้นทางนี้ใช้ HTTP และ JSON เพื่อให้โปรแกรมอื่นอ่านหรือจัดการข้อมูล เริ่มด้วย standard library `net/http` ไม่ต้องใช้ framework ตั้งแต่โปรแกรมแรก Echo หรือ Gin เป็นทางเลือกภายหลังตามงานที่ต้องใช้

| งานหลักที่ใช้จัดบทเรียน | วิธีตรวจผล | นำไปต่อยอด |
|---|---|---|
| เปิด server บน loopback แล้วตอบข้อความ | เรียกหนึ่งเส้นทางและปิดโปรแกรมได้ | พื้นฐานบริการ |
| รับ request และส่ง JSON หนึ่งรายการ | status และข้อมูลตรงกับที่คาด | API อ่านข้อมูลการวัด |
| เรียกกฎจาก Phase 2 | input เดียวกันให้ผลตามกฎเดิม | ใช้กฎเดียวกันจากหลายช่องทาง |
| แยก handler และ use case | ทดสอบกฎโดยไม่เปิด server และตรวจคำตอบ HTTP ด้วย httptest | แยกหน้าที่รับส่งข้อมูลกับขั้นตอนงาน |
| เพิ่มข้อมูลในหน่วยความจำ | รับ POST และอ่านกลับได้ | พื้นฐาน CRUD: เพิ่ม อ่าน แก้ ลบ ทีละอย่าง |
| ตรวจ input และตอบ error | JSON เสีย/ข้อมูลไม่ครบ/ไม่พบรายการ | ผู้เรียกเข้าใจเหตุที่ล้มเหลว |
| ขอบเขต request และ timeout | ปฏิเสธ request ที่เกินขนาด และจำกัดเวลาประมวลผล | พื้นฐานบริการที่ควบคุมได้ |
| ทดสอบ handler และหยุด server | ใช้ httptest และตรวจ shutdown | หลักฐานพฤติกรรม API |

**Handler** แปลง HTTP request/response ส่วน **use case** ดูแลงาน เช่น ตรวจและบันทึกข้อมูลการวัด กฎของงานไม่ผูกกับชนิด request/context ของ framework โดยตรวจรูปแบบ JSON ที่ handler และตรวจเงื่อนไขของการวัดในส่วนกฎ

ผลจบเฟส: API บน localhost ใช้ข้อมูลในหน่วยความจำ เริ่มใหม่แล้วข้อมูลหายได้โดยตั้งใจ เพื่อให้เห็นเหตุผลที่ต้องมี Phase 4 ยังไม่เปิดรับสาธารณะหรือทำ authentication/deployment ในบทเปิด server แรก

## Phase 4 — Database / Persistence และการจัดโครงสร้าง

**Persistence** หมายถึงเก็บข้อมูลให้ยังอยู่หลังโปรแกรมจบ เริ่มจาก SQLite ซึ่งเก็บฐานข้อมูลเป็นไฟล์ เพื่อให้เรียนแนวคิดได้ก่อนดูแล database server แล้วค่อยมี PostgreSQL เป็นทางเลือกเมื่อมีเหตุผลด้านหลายผู้ใช้/การติดตั้งบริการ ไม่ติดตั้งทั้งสองพร้อมบทแรก

| เป้าหมายย่อย | วิธีตรวจผล | นำไปต่อยอด |
|---|---|---|
| ตาราง แถว คอลัมน์ และ SQL พื้นฐาน | สร้างตารางเล็ก เพิ่มแล้วอ่านหนึ่งรายการ | เข้าใจโครงสร้างก่อนเรียกผ่าน Go |
| ใช้ database/sql และ driver | เชื่อมต่อ เขียน อ่าน และปิดทรัพยากร | เชื่อม Go กับฐานข้อมูล |
| Query ที่ส่งค่าเป็น parameter | ทดลองข้อความที่มี quote โดยไม่ต่อ SQL จาก input | การรับข้อมูลผู้ใช้ |
| นำ API จาก Phase 3 มาใช้ storage ใหม่ | restart แล้วอ่านข้อมูลเดิมได้ | API ที่เก็บข้อมูลถาวร |
| อ่านผลและ error จากฐานข้อมูล | แยกกรณีไม่พบข้อมูลกับการบันทึกล้มเหลว และส่งผลให้ผู้เรียกตัดสินใจ | เตรียมขอบเขตระหว่างกฎกับการจัดเก็บ |
| Migration และ transaction | เปลี่ยน schema อย่างมีลำดับ; งานหลายคำสั่งสำเร็จ/ย้อนกลับเป็นชุด | การเปลี่ยนรุ่นและบันทึกข้อมูลสอดคล้องกัน |
| Event ID, เวลาอ่านเดิม และ unique constraint | ส่ง event ซ้ำแล้วไม่เพิ่มการวัดซ้ำ | เตรียมข้อมูลสำหรับ retry ใน Phase 5 |
| ประวัติและการดูแลไฟล์ข้อมูล | ค้นตามเวลา จำกัดจำนวนผล ทดสอบสำรอง/อ่านกลับในข้อมูลจำลอง | ประวัติการวัดและการกู้ข้อมูล |

เลือกและตรวจรุ่น driver, Go, ความต้องการ C compiler และวิธีติดตั้งเมื่อเริ่มบทนี้จริง `database/sql` เป็น API ร่วมของ Go ไม่ได้มี SQLite driver ติดมาให้โดยอัตโนมัติ ยังไม่ยืนยัน driver หรือการติดตั้งที่ไม่ได้ตรวจ

ผลจบเฟส: API เก็บข้อมูลจำลองและอ่านกลับหลัง restart ได้ พร้อมเงื่อนไขจัดการข้อมูลซ้ำ transaction และ idempotency อยู่หลังพื้นฐานการบันทึกและอ่านข้อมูล

### ช่วงท้าย: ปรับโครงสร้าง API ที่เชื่อมฐานข้อมูลแล้ว

ใช้ API เดิมเป็นงานต่อเนื่อง ก่อนเริ่มต้องบันทึก อ่านกลับ และทดสอบ restart ได้ **Refactor** หมายถึงปรับโครงสร้างโค้ดโดยรักษาพฤติกรรมที่ตกลงไว้ ช่วงนี้ยังเป็นแผนบทเรียน ไม่มีโค้ดหรือผลทดสอบใหม่

| งานหลัก | ลงมือทำ | เกณฑ์ตรวจเมื่อจัดทำบท |
|---|---|---|
| แยกกฎและข้อตกลงการจัดเก็บ | ให้ use case ใช้ interface ที่ระบุเฉพาะงานที่ต้องใช้ ส่วน SQL อยู่ในตัวจัดเก็บ | ข้อมูลผิดไม่ถูกส่งไปบันทึก และ error จากตัวจัดเก็บถูกส่งกลับ |
| ประกอบ HTTP, use case และฐานข้อมูล | ส่งส่วนที่ต้องใช้ผ่านฟังก์ชันสร้าง แล้วเชื่อมใน main จัด cmd/internal ตามขอบเขตงาน | คำตอบ API เดิมยังตรงตามที่กำหนด และข้อมูลอยู่หลัง restart |
| ทดสอบแต่ละส่วนและเส้นทางจริง | ใช้ตัวจัดเก็บจำลองทดสอบกฎ และฐานข้อมูลชั่วคราวทดสอบ SQL กับ transaction | ตรวจเส้นทางสำเร็จ ล้มเหลว ข้อมูลซ้ำ และ rollback ตามกฎเดิม |

**Clean Architecture** ในที่นี้เน้นทิศทางการพึ่งพา: ส่วนกฎไม่ต้อง import HTTP framework หรือเครื่องมือฐานข้อมูล ดูคำศัพท์ ตัวอย่างโครงสร้าง และขอบเขตการทดสอบใน [เส้นทางจัดโครงสร้างโค้ด](ARCHITECTURE.md)

ผลที่ตั้งใจไว้เมื่อจบช่วงนี้: API เดิมทำงานได้โดยแยกหน้าที่ชัดเจน พร้อมหลักฐานการทดสอบก่อนและหลังปรับโครงสร้าง จำนวน EP จะกำหนดเมื่อจัดทำเนื้อหาจริง โดยรวมขั้นที่ใช้แก้งานเดียวกันไว้ด้วยกัน

## Phase 5 — IoT / Edge Gateway

ต้องเข้าใจ Phase 2 และพื้นฐานการบันทึกข้อมูลใน Phase 4 ก่อนทำการทดลอง ACK ครบเส้นทาง เริ่มตัวจำลองก่อนทุกครั้ง

| เป้าหมายย่อย | การทดลองหลัก | สิ่งที่ต่อยอด |
|---|---|---|
| อุปกรณ์จำลองและ event | event ID และเวลาอ่านถูกกำหนดตอนอ่าน ไม่สร้างใหม่ตอน retry | ตัวตนข้อมูลตลอดเส้นทาง |
| หลายอุปกรณ์ | ตัวหนึ่ง timeout/ล้ม อีกตัวยังทำงาน | แยกผลกระทบของความเสียหาย |
| แยกตัวอ่าน คิว และตัวส่ง | ใช้ข้อตกลงจากงานจริง แล้วสลับตัวจำลองให้แต่ละส่วนล้มเหลวได้ | ทดสอบกฎโดยไม่ต้องพึ่ง broker ทุกกรณี |
| MQTT ในเครื่อง | broker/topic/publish/subscribe/QoS ทีละเรื่อง | ส่งข้อมูลจำลอง |
| เก็บก่อนส่ง | บันทึกลงดิสก์แล้วจึงส่ง ตรวจเมื่อเขียนไม่สำเร็จ | คิวข้อมูล offline |
| ส่งย้อนหลัง | หยุด broker → เก็บค้าง → เริ่มใหม่ → retry | store-and-forward |
| ผู้รับและ ACK สองระดับ | ใช้การบันทึกจาก Phase 4; แยก PUBACK จาก ACK หลัง commit ฐานข้อมูล | เงื่อนไขลบข้อมูลออกจากคิว |
| restart และข้อมูลซ้ำ | restart ตามจุดสำคัญ/ACK หาย/ส่งซ้ำ | ตรวจด้วย event ID เดิม |
| เพดานพื้นที่ | คิวขนาดเล็กเต็ม/ไฟล์ท้ายขาด ไม่ทำดิสก์จริงเต็ม | นโยบายเมื่อรับข้อมูลต่อไม่ได้ |

ผลจบเฟส: Gateway จำลองและผู้รับบน localhost ที่มีหลักฐานการทดสอบบางกรณี พร้อมข้อจำกัดชัดเจน ไม่อ้าง exactly-once ทั้งระบบหรือ production-ready

## ทางเลือกในการต่อยอด

หลังเรียน API และ Database สามารถต่อยอดด้วยหน้าแสดงผลที่เรียกข้อมูลจาก API ได้

ใช้การแบ่งหน้าที่จากท้าย Phase 4 ต่อกับ Gateway โดยยังต้องทดสอบดิสก์และ MQTT จริงในเครื่อง ตัวจำลองไม่ได้ยืนยันพฤติกรรมของระบบภายนอก

ค่อย ๆ นำส่วนที่เรียนมาประกอบเป็นโปรเจกต์เดียว ก่อนนำไปใช้กับระบบจริงจะต้องศึกษาข้อจำกัดและทดสอบเพิ่มเติม

## เหตุผลที่เพิ่ม API และ Database ก่อน Gateway

Phase 3–4 ให้พื้นฐานการสร้างบริการและบันทึกข้อมูลก่อนถึง Gateway เพื่อให้เข้าใจว่า “ผู้รับบันทึกสำเร็จ” หมายถึงอะไร และไม่ต้องเรียน SQL, transaction, HTTP server และ MQTT พร้อมกัน

ทุกบริการผูกกับ loopback เท่านั้น ใช้ข้อมูลจำลอง ไม่มีการใช้ IP/รหัสผ่านบริษัทหรืออุปกรณ์ production ไม่ต้องใช้ Docker ใน Basic เริ่มติดตั้ง dependency เพิ่มเมื่อถึงบทที่จำเป็นและตรวจรุ่นใหม่อีกครั้ง
