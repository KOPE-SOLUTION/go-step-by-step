# เส้นทางจัดโครงสร้างโค้ด

**สถานะ: แผนสำหรับ Phase 2–5** ใช้ต่อจากพื้นฐาน 14 EP ยังไม่มีโค้ด API หรือฐานข้อมูลให้รันในหน้านี้ เริ่มเรียนพื้นฐานได้จาก [สารบัญ Phase 1](playlist-01-go-basic/README.md)

เรียนผ่านโปรแกรมข้อมูลการวัดตัวเดิม: ทำให้ทำงานได้ → พบส่วนที่ต้องแยก → ปรับโครงสร้าง → ตรวจด้วย test ว่าพฤติกรรมยังถูกต้อง

## คำศัพท์ที่ใช้

| คำ | หน้าที่ในตัวอย่าง |
|---|---|
| Business rule | กฎของงาน เช่น ชื่ออุปกรณ์ต้องไม่ว่าง |
| Handler | รับ HTTP request และแปลงผลเป็น HTTP response |
| Use case | ขั้นตอนงาน เช่น ตรวจการวัดแล้วสั่งบันทึก |
| Repository / Store | ส่วนที่อ่านหรือบันทึกข้อมูลตามข้อตกลงที่ผู้เรียกต้องการ |
| Adapter | โค้ดเชื่อมกับรายละเอียดภายนอก เช่น HTTP หรือ SQL |
| Dependency injection | ส่งสิ่งที่ส่วนหนึ่งต้องใช้เข้ามาจากผู้เรียก เช่น ส่งตัวจัดเก็บให้ use case |
| Refactor | เปลี่ยนโครงสร้างภายใน โดยรักษาพฤติกรรมที่ตกลงไว้ |

## เรียนเมื่อไร

| ช่วง | งานที่ทำ |
|---|---|
| Phase 1 — พื้นฐานที่มีแล้ว | EP.11 ฝึก interface; EP.12 แยก package; EP.13–14 ทดสอบกฎและแยกการประมวลผลจากการพิมพ์ |
| Phase 2 | แยกการอ่านไฟล์หรือเรียก HTTP ออกจากกฎ ส่งตัวอ่านที่ต้องใช้เข้าฟังก์ชัน |
| Phase 3 | ให้ handler รับส่ง HTTP ส่วน use case ทำงานกับข้อมูล Go ธรรมดา แล้วทดสอบแยกกัน |
| Phase 4 | เริ่มด้วย API ที่บันทึกฐานข้อมูลได้ก่อน จากนั้นปรับขอบเขตของกฎ ตัวจัดเก็บ และการประกอบส่วนต่าง ๆ |
| Phase 5 | ใช้แนวคิดเดิมกับตัวอ่านอุปกรณ์ คิวบนดิสก์ และตัวส่ง MQTT เพื่อจำลองความผิดพลาดได้ |

งานและเกณฑ์ตรวจของแต่ละช่วงอยู่ใน [แผน Phase 2–5](FUTURE_ROADMAP.md)

## หลักที่ใช้เมื่อปรับโครงสร้าง

Clean Architecture ให้ความสำคัญกับทิศทางการพึ่งพาของโค้ด ส่วนที่กำหนดกฎไม่ควรรู้รายละเอียด HTTP framework หรือ SQL driver และจำนวนชั้นเลือกตามงาน [หลักการต้นฉบับ](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)

ในตัวอย่างของเรา:

- ส่วนการวัดกำหนดชนิดข้อมูล กฎ และ interface ของตัวจัดเก็บเท่าที่ต้องเรียกใช้
- ส่วน HTTP แปลงข้อมูล request ก่อนส่งให้ use case และแปลงผลกลับเป็น response
- ส่วน SQL ทำตาม interface โดยแปลงข้อมูลที่จำเป็นต่อการจัดเก็บและตรวจ error
- main สร้างฐานข้อมูล ตัวจัดเก็บ และ use case แล้วส่งให้ handler ใช้

แม้ตอนรัน use case จะเรียกตัวจัดเก็บ แต่โค้ด use case รู้จักเพียง interface ของตนเอง ไม่ต้อง import package ของ SQL การเรียกงานกับทิศทาง import จึงเป็นคนละเรื่อง

กฎ เช่น “ข้อมูลซ้ำควรได้ผลอย่างไร” อยู่ฝั่งงาน ส่วนรูปแบบคอลัมน์และการแปลงเวลาสำหรับ driver อยู่ฝั่งจัดเก็บ เลือกตำแหน่งจากเหตุผลที่ข้อมูลต้องเปลี่ยน

## โครงสร้างที่อาจใช้เมื่อโปรแกรมโตขึ้น

นี่เป็นตัวอย่างสำหรับช่วงท้าย Phase 4 ยังไม่ต้องสร้างโฟลเดอร์เหล่านี้ในพื้นที่ฝึกพื้นฐาน

```text
cmd/api/
  main.go                 # ประกอบส่วนต่าง ๆ และเริ่มบริการ
internal/measurement/
  reading.go              # ข้อมูลและกฎ
  service.go              # ขั้นตอนงานและ interface ที่ต้องใช้
  service_test.go
internal/httpapi/
  handler.go              # แปลง HTTP เข้าและออก
internal/sqlstore/
  store.go                # ติดต่อฐานข้อมูล
go.mod
```

เอกสาร Go แนะนำ cmd/internal สำหรับบริการตามบริบทของโครงการ ส่วนชื่อ measurement/httpapi/sqlstore เป็นทางเลือกของตัวอย่างนี้ [การจัด Go module](https://go.dev/doc/modules/layout)

## เลือกเครื่องมือเท่าที่จำเป็น

- สร้าง interface จากการใช้งานจริง โดยทั่วไปวางไว้ฝั่งผู้ใช้ ไม่ต้องมีหนึ่ง interface ต่อหนึ่ง struct หรือทุกชั้น [แนวทาง Go](https://go.dev/wiki/CodeReviewComments#interfaces)
- ใช้ฟังก์ชันสร้างและ parameter สำหรับส่งส่วนที่ต้องใช้ก่อน ยังไม่ต้องมี framework สำหรับ dependency injection
- เริ่ม API ด้วย net/http และฐานข้อมูลด้วย SQL กับ database/sql ตามแผนเดิม Echo, Gin, GORM และ Docker เป็นทางเลือกที่ต้องมีเหตุผลและตรวจเวอร์ชันเมื่อถึงบท
- การเปลี่ยนฐานข้อมูลยังอาจต้องปรับ SQL, schema และ transaction การมี interface ไม่ได้ทำให้ฐานข้อมูลทุกชนิดใช้แทนกันได้ทันที
- ใช้ interface แยกจุดเชื่อมต่อเมื่อมีประโยชน์ ส่วนฟังก์ชันและ struct ธรรมดายังเหมาะกับกฎที่เรียบง่าย

## ตรวจว่าการแบ่งส่วนช่วยจริง

ก่อนปรับโครงสร้างให้เก็บ test ของพฤติกรรมที่ต้องรักษา: คำตอบ API ข้อมูลที่อ่านกลับ และกฎการรับข้อมูล

| วิธีตรวจที่วางแผนไว้ | สิ่งที่ต้องเห็น |
|---|---|
| Unit test กับตัวจัดเก็บจำลอง | ข้อมูลผิดไม่ถูกบันทึก; บันทึกไม่สำเร็จต้องไม่รายงานว่าสำเร็จ |
| HTTP test ด้วย httptest | request, status และ response ยังตรงกับข้อตกลงเดิม |
| Integration test กับฐานข้อมูลชั่วคราว | schema, SQL, ข้อมูลซ้ำ และ transaction ทำงานตามกฎ |
| ทดลอง restart กับข้อมูลจำลอง | ข้อมูลที่ยืนยันว่าบันทึกแล้วอ่านกลับได้ |

Integration test คือการตรวจหลายส่วนทำงานร่วมกัน ตัวจัดเก็บจำลองใช้ตรวจขั้นตอนงานได้ แต่ยืนยันว่า SQL หรือดิสก์จริงทำงานถูกต้องไม่ได้ การทดสอบข้างต้นยังเป็นเป้าหมายของบทที่จะสร้าง
